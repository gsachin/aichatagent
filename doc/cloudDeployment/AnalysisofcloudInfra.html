Based on the system information provided for your University Admissions Voice AI Assistant, the overall infrastructure is well-designed for a single-stream/local environment. However, real-time audio processing over telephony/WebSockets imposes strict latency (under 300ms–500ms total pipeline target) and concurrency demands.

Below are the key infrastructural and architectural updates needed to transition this setup into a production-ready, ultra-low-latency, real-time voice system.

1. Concurrency & GPU VRAM Allocation

🚨 The Latency & Concurrency Bottleneck

  • In-Process VRAM Budgeting: The current budget allocates ~5.65 GB on a 6 GB card (e.g., RTX 2060). While this works for 1 call, concurrent calls will quickly hit CUDA Out-Of-Memory (OOM) errors or severe queuing delays because Ollama KV caching, Whisper buffers, and Kokoro ONNX run in the same GPU space.
  • Sequential Pipeline Delays: Processing STT → RAG → LLM → TTS sequentially per user utterance causes conversational lag (turn-taking delays of 2–4+ seconds on low-tier GPUs like T4).

🛠️ Recommended Updates

  1. Upgrade GPU Instance:

  • Minimum for single call / dev: NVIDIA T4 (16 GB VRAM).
  • Minimum for production (5–10 concurrent calls): NVIDIA L4 (24 GB VRAM) or A10G. The extra VRAM is essential for Qwen 2.5 7B's KV cache growth across simultaneous user sessions.
  1. Decouple Ollama & Dynamic GPU Offloading:

  • Run Ollama as an independent service container with explicitly pinned context limits (OLLAMA_NUM_PARALLEL=4) to handle multi-threaded completions without locking the WebSockets server thread.

2. Telephony & WebSocket Architecture (Twilio Streaming)

🚨 Real-Time Audio Constraints

  • u-Law Decoding Overhead: Twilio streams 8kHz mulaw audio chunks. Converting 8kHz mulaw $\leftrightarrow$ 16kHz PCM (required by Whisper) inside Python standard threads can block the FastAPI event loop during high inbound traffic.
  • Lack of Interruptibility (Barge-in): If a user speaks while the bot is streaming TTS back to Twilio, the bot will continue playing cached TTS audio unless explicitly cleared. Twilio requires outbound audio clear frames when user speech is detected.

🛠️ Recommended Updates

  1. Implement Twilio Audio Interruption & Buffer Management:

  • Send a clear message event to the Twilio WebSocket stream as soon as faster-whisper or VAD (Voice Activity Detection) registers new user speech.
  1. Add Silero VAD (Voice Activity Detection):

  • Do not pass continuous raw WebSocket audio chunks to Whisper. Insert an ultra-lightweight Silero VAD stage (runs on CPU/CUDA in <5ms) to segment audio dynamically into speech/non-speech chunks before calling STT.
  1. Use WebSockets Streaming / Chunked TTS Generation:

  • Instead of generating full audio responses with Kokoro-82M before sending them back, stream text tokens directly from Ollama/Qwen into Kokoro, emitting 200ms–500ms audio frames over the WebSocket as soon as sentence boundaries or punctuation marks are reached.

3. High Availability & Architectural Decoupling

🚨 In-Memory State Vulnerability

  • Single Point of Failure (SPOF): The system summary notes that _active_call_sids, _transcript_events, and _batch_jobs reside in-memory inside FastAPI. If the container restarts or crashes during a live call, the WebSocket breaks, and the state is lost.
  • Scalability Lock: Horizontal scaling (e.g., placing FastAPI behind an AWS ALB) is impossible without sticky sessions because live calls depend on local RAM states.

🛠️ Recommended Updates

  1. Redis for Session & State Management:

  • Shift in-memory call buffers and state identifiers (_active_call_sids) out of FastAPI and into Redis Cloud / ElastiCache.
  1. Process Separation:

  • Split the Streamlit dashboards (app.py, dashboard.py) into a separate lightweight CPU-only container. Do not share the GPU/Inference compute instance with admin UI serving.

  3. WebSocket Keep-Alives: When deploying Caddy / Nginx / Traefik as the TLS reverse proxy for TUNNEL_HOST, explicitly raise the WebSocket read/write timeout settings:
