DSPMU · NGA post-mortem 2026-10-31 Analysis only · no code changed

Why the recent fixes did not fix the chat

The agent is failing before its retrieval layers run. Four implicit contracts — conversation, navigation, evidence adequacy, and answer state — are broken, and every recent fix sits downstream of them.

Scope NGA text / chat / WhatsApp Evidence live graph copy · turn events · answer cache · reproductions · live site probes Verdict contract mismatch cascade
Bottom line

The system is a retrieve-then-generate question answerer with a citation verifier, not a conversational assistant. It decides, before any of the new machinery runs, that a conversation move is a knowledge query, that a shell page does not exist, that any retrieved text is adequate evidence, and that a refusal with no false claim is a verified answer.

Those four decisions produce the observed experience: meta questions get knowledge answers, programme questions get refusals, deep search never fires, a legitimate M.Sc. answer is blocked by a UG alias table, and the refusal is cached for a day.

01

What the work meant to do

The intent is not ambiguous. It is a live-site, conversational, navigation-grounded agent. The implementation is a one-shot lexical search plus an evidence-constrained LLM.

The design set states the problem as a solution-design failure, not a website-availability failure: the runtime has no path to most of the live site. The product intent is to “make any published DSPMU website detail answerable, in real time, in the user’s channel and language, with a grounded and cited response.”

The agent is required to know the site hierarchy, navigate it through constrained tools, combine verified facts with live page content, keep a durable conversation record that improves follow-up retrieval, and degrade to the static answer only when the live site or a tool fails.

North star

≥ 90% grounded live-answer rate

M-01 on a frozen evaluation set. M-02 requires 100% critical-fact accuracy; M-09 requires every turn to have a plan, tools, evidence, answer, verifier result and latency.

Product promise

Any published detail

Not “any page whose title shares a token with the question.” The intent explicitly names library timings, the Vice-Chancellor, hostel process and the Grievance Redressal Cell as the failure cases.

Conversation

Follow-ups resolve

JTBD-06: “what about its fee?” after opening a topic must resolve the topic, programme and time scope without a full transcript stuff.

Architecture thesis

Navigate, don’t just search

Typed graph + tools + planner + evidence + verifier + event memory. The graph is meant to preserve hierarchy and per-node metadata, not merely feed a title FTS index.

The 2026-10-31 amendment added hybrid retrieval, a chunk corpus, a time-scoped cache and a deep-search fallback. Its own diagnosis was that the current path “misses facts that exist on the live site but are not indexed” and can reuse a cached answer outside the period the user asked about. That diagnosis was correct — but the response was applied one layer too low.

The failure, in the system’s own records

The recent conversation is the clearest evidence. It is not a handful of isolated bugs; it is the four contracts failing in sequence.

What the user saw

  • Turn 1: a meta request (“can you search deep”) answered as a site query, with an irrelevant bundle and a canned offer to search.
  • Turn 2: a direct programme-list question answered with a refusal, even though department pages in the graph contain “U.G History / P.G History / Syllabus & Course Documents” and the live site’s /search?q=programmes returns the Academic Programmes and department pages. The refusal is cached as verified for 24 hours, so repeating the question returns the same refusal.
  • Turn 3: a meta question about the assistant’s understanding was routed to the date/notice path because the classifier sees “when.” It produced a plausible-sounding but unsupported answer with a citation to the About page.
  • Turn 4: the user explicitly asked for deep search. The planner produced a site.search; the evidence bundle was non-empty (irrelevant), so deep search was never called. The answer was blocked by the verifier and rendered as “I could not find a verified answer in the public university pages. Please contact the registrar.”

Two other cache entries show the same pattern. happending → “I checked the official university website for the latest details. I could not verify…” → verified, cached for 1 hour: the deep-search refusal path found something, could not answer, prefixed a message that claims it checked the site, and cached the non-answer. search deep → “Yes—what would you like me to search for at DSPMU…” → verified, cached 24 hours.

The only demonstrated successes were vice chancellor (“The Vice Chancellor is Prof. Rajiv Manohar.”) and exam schedule oct 2026 (“The schedule lists exams on 13-10-2026.”). That is exactly the profile of a lexical QA system: it works for distinctive noun phrases whose answer is in an indexed page or fact, and fails for conversational acts, broad enumeration, synonyms, PG entities and shell-shaped sections.

The navigation contradiction

The intent says the agent must navigate empty CMS shells and follow documents. The code makes empty shells invisible to every tool. A shell is useless as evidence, but it is valuable as a navigation node: it has a URL, title, parent, children and often links to documents. The implementation conflates “cannot ground a claim” with “does not exist.”

The Academic Programmes node is not in the top 20; it is excluded as an empty shell. The closest useful page, faculties.vocational-studies (“Self-Finance and Vocational Courses”), is not retrieved either. A department page such as departments.history contains “Under Graduate / U.G History / Post Graduate / P.G History / Syllabus & Course Documents” but is not in the top 20.

The scoring still has the old shape: unweighted term overlap across title, nav, alias, path and section; BM25 capped at min(2.0, -rank × 0.25); content bonus 2.5 for HTML; authority bonus 1.0; no IDF, no field weighting, no stemming, no relevance threshold. _GENERIC_TOKENS only drops “university”, “universities” and “upcoming”; “currently”, “list”, “programs”, “offered” and “details” remain as ranking terms.

nga_fts is fts5(..., tokenize='unicode61'); there is no porter stemmer. So programs does not match programme; courses does not match course; lists does not match list.

Information Technology” from the evidence is therefore treated as claiming “B.Sc. Information Technology,” which is not in the evidence, and the answer is blocked as a critical programme failure. This is a concrete, reproducible cause of a legitimate answer being thrown away. It is also a warning about reusing a lead-capture entity detector as a grounding verifier: the two have different universes.

4.5 The planner never navigates

The deterministic planner’s entire output surface is:

fee / programme / page_topic  -> site.search
notice / date                 -> site.latest, maybe + site.search
contact                       -> site.search "contact registrar"
follow-up                     -> site.open(current_node) [+ site.search]
boundary                      -> no steps

For ten representative questions, site.navigate, site.documents, site.follow and site.freshness never appeared. The navigation graph is used only as a ranking index. JTBD-02 (“navigate the hierarchy when the exact page is unknown”) is not implemented in the live default path. A broad question like “list all programmes offered” cannot be answered by a top-3 search; it needs an open-section-and-enumerate plan or a structured catalogue.

assemble_evidence() has no relevance gate. It takes the successful tool results and adds them, up to the item/character caps. So “library timings” returns exam-timing PDFs, “what programmes are offered” returns NEP/NSS pages, “hostel rules” returns a 2022 fee PDF and About pages, and “can you check deep search…” returns the Grievance Portal and M.Sc. The live site’s own /search endpoint returns the right pages:

/search?q=library timings  -> /facilities/central-library, /cms/central-library,
                              /academic-programmes/ug, /academic-programmes/pg,

The deep-search service uses exactly this endpoint. It is the correct escape hatch. It is simply never reached because the bundle has junk in it.

4.7 The live site is shell-shaped and image-shaped

I probed the live pages. /cms/academic-programmes, /academic-programmes/ug and /academic-programmes/pg return ~5,500 characters of HTML, almost all navigation/footer; the content area is empty. /facilities/central-library and /cms/central-library return ~1,000 characters after stripping scripts/nav/header/footer: 11 images, alt “Library,” no timing text. /student-life/hostel and /cms/hostel are “Hostel Gallery” shells.

The graph’s empty_shell labels are factually correct for the extracted HTML. The problem is the assumption that the CMS HTML is the primary public surface. For these pages it is not. The information a human sees in a browser may be in images, JS-rendered blocks, the old site, department pages or PDFs. The current knowledge plane cannot see it, and the deep-search fallback rejects any page under 80 characters of text — exactly these shells.

The answer to “the information is already on the website”

It is available to a human browser, but not to the HTML-only retrieval pipeline. Adding chunks, embeddings or a cache over the same extracted text cannot retrieve content that was never extracted. The pipeline needs a different acquisition strategy for these pages, or an explicit statement that they are not machine-readable and a hand-off to the published URL/contact. Right now it produces a generic refusal indistinguishable from “the university does not publish this.”

4.8 The verifier verifies claims, not answers

A refusal such as “I couldn’t verify which programmes are currently offered…” contains no amounts, dates, URLs, emails, phones, named people or detectable programmes. It therefore has no claims, no failures, and returns status="verified". The cache stores that as a verified entry for 24 hours. The next identical question returns the refusal without calling the LLM.

The same contract flaw is why the blocked turn renders as “I could not find a verified answer in the public university pages.” The user cannot tell whether the system found nothing, found something but rejected its own answer, or hit a policy boundary. In turn 4 it had evidence and the LLM produced something; the verifier blocked it; the user was told the university pages had no verified answer. That statement is false.

4.9 The cache makes one bad turn sticky

The cache key includes normalized query, language, channel, programme, time scope, index version and policy version. It does not include the answer type (answer vs refusal vs clarification), the conversation topic/current node, the chunk index version, or the embedding model/version. _cache_versions() uses only the graph compile run, so rebuilding the chunk index does not invalidate the cached refusal.

Revalidation only runs near expiry. For an entry with no source URL, it returns valid=True, checked=False, "no_source" — a cached refusal with no citations is treated as valid without a check. A refusal with citations to unchanged junk pages survives revalidation. This is why “multiple attempts” produce the same answer: the first failure is not just displayed; it is promoted to a verified cache fact.

4.10 The conversation path is not wired

plan_text() constructs a fresh SessionState(language=language) every turn. ConversationMemory.load() and .plan() exist but build_text_answer() calls neither. It only calls .record() at the end of the normal path, and even that is skipped for cache hits and deep-search returns.

The Streamlit path calls query_rag_stream(prompt, ...) with agentic_text, channel and conversation_id, but no history. query_rag_stream() has no history parameter. The synchronous path has one and passes it to build_text_answer, but that function uses it only in the generation prompt; the planner still gets fresh state. So even on WhatsApp, “what about its fee?” cannot resolve “it” at retrieval time. The Phase 6 demo worked because the demo passed a SessionState explicitly; the live seam never does.

4.11 Serving and indexing share one SQLite writer

At analysis time, scripts/nga_documents.py --backfill --chunks was running at ~90% CPU and held many file descriptors on content/dspmu/nga_graph.sqlite3. Reads from the live database failed with database is locked, including read-only queries. The store uses sqlite3.connect(..., timeout=30.0), PRAGMA busy_timeout = 30000, and the database is in journal_mode=delete (not WAL).

The answer path and the batch indexer use the same file. A long document backfill can make a user turn wait up to 30 seconds, exceed the 8-second text deadline, raise inside build_text_answer, and silently fall back to the static path. That is a reliability/architecture defect, not a retrieval bug, and it explains inconsistent behavior during testing.

4.12 The profile gate can hijack the first turns

This is a channel-level issue in app.py, separate from the NGA core, but it contributes to “not responding as expected of a conversation.” On first load, awaiting_field is set to "name". Any message that is not recognised as a question, admission intent, skip word or short name is treated as a name. “Tell me about the university” (5 words, no ?, no keyword) becomes “That’s a bit long for a name. Could you just tell me your first and last name?” “hello” is short enough to be stored as the user’s name. A message containing “admission” starts the lead-capture flow rather than answering the admission question.

The observed conversation got past this gate, so it is not the cause of turns 1–4. But the first-run experience is a lead form, not a chat, and that is part of what the user is describing.

05

Four broken contracts

These are not module bugs. They are implicit decisions that make the current failure likely even if every module is correct.

Contract 1

Conversation

Current: every message is a standalone knowledge query. No small talk, meta, clarification or follow-up state.
Required: a dialogue frame with dialogue act, resolved query, topic, programme, time scope and requested shape, loaded from conversation memory before planning.

Contract 2

Navigation

Current: empty_shell nodes are unanswerable for search and navigation; the planner never calls site.navigate.
Required: separate “can ground” from “can navigate.” A shell is a route, not evidence.

Contract 3

Evidence adequacy

Current: any non-empty bundle is evidence. No relevance, coverage or shape check.
Required: an explicit predicate; if inadequate, navigate, deep-search, clarify, or refuse with a reason — never treat junk as adequate.

Contract 4

Answer state

Current: “verified” means “no unsupported claim.” Refusals are verified and cached.
Required: separate claim support from answer adequacy; an explicit answer state machine; only positive answers receive a positive cache TTL.

D1. The product contract is conversational; the implementation is one-shot QA

The design promises a conversation record that improves follow-up retrieval, but the live answer contract is “query → retrieve → generate → verify.” There is no dialogue-act model, no clarification state, no small-talk path, no follow-up frame. The only conversation state is a typed SessionState that the live path never loads. Adding more retrieval cannot make a search box conversational.

D2. The navigation contract is contradicted by the answerability policy

The architecture claims the typed graph preserves hierarchy and lets the agent navigate. But is_answerable() removes empty_shell, soft_404, unreachable, removed and blocked nodes from search and navigation, not just evidence. The site’s programme, hostel and library sections are shells. The agent cannot navigate the exact sections the design was built for.

The correct distinction is evidence answerability (can this text ground a claim?) vs navigation answerability (can this node be a route with metadata/children/links?). The code collapses both into one predicate.

D3. “Verified” conflates claim safety with answer adequacy

The verifier answers “is every critical claim supported?” It does not answer “is this a responsive answer?” A refusal has no claims, so it is safe and verified. A correct answer that mentions a PG programme is unsafe according to the UG-only detector, so it is blocked. Safety and correctness are different axes, and the system has only one axis.

D4. Evidence has no relevance or sufficiency predicate

The decision to stop retrieving and start answering is “the bundle is non-empty.” That is not a sufficiency test. A usable predicate needs top relevance, query-term coverage, evidence type/shape match, time-scope coverage and entity-catalogue match for list questions. Without it, junk evidence is indistinguishable from good evidence, deep search is suppressed, and the LLM is asked to answer from noise.

D5. The knowledge model is page-centric in an entity/catalogue-shaped site

The useful knowledge is spread across department pages, PDFs, shell pages that are navigation hubs, image galleries, legacy pages and the site’s own search index. The system models “a page with text” as the unit of knowledge. It has no first-class programme, department, notice, document, time scope or authority entity that can be queried independently of a page. The facts layer covers only fees, contacts and leadership. A question like “which programmes are offered” is an entity/list query; the system treats it as a page-search query and fails.

D6. The product scope and the policy boundary contradict each other

The intent says “any published detail,” and the evaluation catalogue includes “Postgraduate programs” and “Doctoral / PhD programs.” But the programme detector is UG-fee-only; PG programme/fee/seat/eligibility requests can be answered with a deterministic boundary refusal; and the boundary heuristic is inconsistent: "list of postgraduate courses" is blocked, while "what PG programmes are offered" is not. The verifier will block an answer that mentions a PG programme that the detector maps to a UG programme.

The product needs an explicit decision: are PG programme lists (not fees) answerable from public pages? If yes, build a PG catalogue and adjust the detector/verifier. If no, say so in the UX and do not promise “any published detail.”

D7. Serving and indexing share one SQLite writer

Even in the local demo, the answer path and a 4,461-document backfill share one delete-journal SQLite file. A batch job can block user turns, and the fallback is silent. The serving store and the indexing store should be separate, or the indexer should write a snapshot and swap it atomically, with WAL and a bounded busy timeout.

Process and engineering

  • P1. Evaluation was last. The README lists Phases 1–12 as implemented and Phase 13 (“Evaluation, dashboards, canary and default-on”) as remaining. The user became the evaluator. The design set’s own Definition of Done requires the evaluation shape and gates before implementation; M-01 is the North Star.
  • P2. Tests validate components, not outcomes. The agent tests build a one-page fixture and inject a fake LLM. The 103-case golden set is checked only for well-formedness, not run against the agent. There is no test for empty-shell navigation, plural programme intent, PG collisions, refusal caching, deep search on low relevance, or a live follow-up.
  • P3. Status documents overstate completion. “Implemented” means “the code path exists.” The amendment lists “deep-search fallback — implemented,” “chunk + embedding hybrid — implemented,” and then, in the same table, “graph write-through is still a follow-up,” “live chunk backfill waits for the document job.” A reader can easily conclude the capability is live.
  • P4. Fixes are compensation layers on broken upstream contracts. Broken conversation → add optional LLM planner (off). Broken retrieval relevance → add chunks/embeddings (empty/off). Broken answer adequacy → add deep search (gated on empty bundle). Broken cache correctness → add time scope/revalidation (refusals cached). Broken verification → add span citations (UG detector blocks PG). Broken coverage → add document backfill (same SQLite writer). Each layer assumes the previous gate produced a meaningful signal. None fixes the gate.

09

What to do instead

Follow the causal order, not the layer order. Do not add another retrieval mechanism until the upstream contracts are explicit.

9.1 Make the four contracts explicit

Contract 1 · Conversation frame

Every turn must carry conversation_id, turn_id, channel, language, dialogue_act (greeting / meta / thanks / backchannel / knowledge / followup / boundary / clarify), resolved_query, topic, programme, time_scope and requested_shape (direct / list / comparison / how-to / confirmation). The planner must receive this frame, loaded from ConversationMemory. Greetings, meta and thanks must not enter retrieval. Update the topic only after a turn that produced a real answer or clarification.

Contract 2 · Retrieval adequacy

Replace “bundle is non-empty” with a predicate: top relevance ≥ T, query-term coverage ≥ C, evidence matches the requested shape, time scope covered if asked, entity-catalogue match for list questions. If not adequate: use a different strategy (navigate, enumerate, site search, child links, PDFs), deep-search, clarify, or refuse with a specific reason. Deep search triggers on not adequate, not not items.

Contract 3 · Answer state machine

answered_verified and answered_rewritten may be cached with a positive TTL. clarification is short-lived. refused_policy, refused_no_machine_text, refused_low_confidence and failed_generation must never be stored under a positive answer status. Add answer_type, topic, evidence_signature, chunk_index_version and embedding_model to the cache schema.

Contract 4 · Navigation answerability

Split is_answerable into can_ground(node) (status OK and not PII) and can_navigate(node) (not blocked/removed/soft-404; a shell is navigable). site.search may return shells with content_status="empty_shell" and groundable=false; site.navigate may return their children/links; site.open returns body_available=false. This is the only way to reach the department pages/PDFs behind the Academic Programmes section.

9.2 Stop the bleeding (same day)

  1. Separate serving from indexing. Stop the backfill against the serving DB or move it to a copy; enable WAL; add a lock/health alarm. The serving process must never share a delete-journal SQLite writer with a batch job.
  2. Purge the bad cache. Delete refusal entries; change _write_answer_cache to never store a no-claim refusal as verified.
  3. Add a relevance gate. Compute query-term coverage and top-score thresholds in assemble_evidence; if below threshold, treat the bundle as empty for both the answer and deep-search decisions.
  4. Trigger deep search on inadequate evidence. Use the site’s /search as a first-class source; follow child links and PDFs; dedupe against the graph.
  5. Fix the programme detector collision. Do not run the UG lead detector against generated answers as a universal programme claim. Add a PG/PhD catalogue, or restrict the verifier’s claim to programmes named in the cited evidence plus the UG fee set. Never map a PG name to a UG canonical name.
  6. Do not render blocked as no-evidence. Say “I found a source but could not verify a specific claim,” include the reason code, and ask a clarifying question when appropriate.
  7. Fix the meta/small-talk path. Add CHITCHAT, META and CLARIFY intents that do not call retrieval.
  8. Fix plural/programme morphology. Normalize programs/programmes/courses; ideally use a porter/unicode61 FTS tokenizer plus a query-expansion alias map. Add tests for both spellings.

9.3 Fix the conversation contract (this week)

  1. In build_text_answer, when conversation_id is present, load SessionState via ConversationMemory.load() (or .plan()), pass it to Planner.plan(), pass recent turns to the answer prompt, and record a turn event on every return path.
  2. Add history/conversation_id to query_rag_stream; let the server load history from conversation_id rather than trusting the client.
  3. Classify the dialogue act before the retrieval planner. Use deterministic rules for greetings/meta/thanks and the LLM planner only for ambiguous knowledge questions.
  4. Make follow-ups work end to end: “what about its fee?” after a hostel page must resolve topic, programme and time scope, and open the current node before searching.
  5. Move Streamlit profile capture out of the answer path; answer first, ask for contact only when the user wants a callback/offer, and make it skippable without hijacking short messages.

9.4 Fix navigation and the knowledge plane (next 1–2 weeks)

  1. Shells as navigation nodes. Return them in search/navigate with groundable=false; expose children/links; site.open says body_available=false.
  2. Use the site’s own search as a retrieval tool, not just a deep-search fallback. It already returns the right pages. Add relevance, allowlist, dedupe, and a fetch policy that follows child links/PDFs.
  3. Build a structured programme/department catalogue from department pages, PDFs and facts: programme(id, name, level UG/PG/PhD, department, duration, eligibility, fee_fact_id, page_url, document_urls, verified_at, source). This is what “list all programmes” needs; it also gives the verifier a correct universe and the planner a list/enumerate plan.
  4. Model content shapes explicitly: page_text, navigation_shell, image_page, pdf, legacy_page, site_search_result. For image/JS shells, decide one of: OCR the published images (bounded, reviewed); use the old site/PDF/department page; render with a browser offline; or hand off with the published URL and contact, clearly labelled. Do not pretend the HTML text is the site.
  5. Planner: add site.navigate/site.documents/site.follow plans for broad/list questions; add a list/enumerate shape; make the LLM planner the default for text chat (validated fallback), or add a deterministic route for departments/programmes.
  6. Write deep-search results back into the graph/chunk index so the next question does not repeat the same live search.

9.5 Fix verification and answer quality

  1. Separate claim verification from answer adequacy. A response can be claim-safe but non-responsive; that is a refusal/clarification, not a verified answer.
  2. Use a programme catalogue for programme claims, not the lead-capture UG fee detector. Compare against the cited evidence and the catalogue level (UG/PG/PhD).
  3. Add a repair loop before refusal: re-prompt once with the failure and the cited evidence; if it fails again, return a targeted clarification, not a generic no-evidence refusal.
  4. Make citations non-fatal to the whole answer when the claim is supported elsewhere in the bundle; repair the citation or accept evidence-level support.
  5. Add a refusal taxonomy and surface it: policy, no_machine_readable_source, low_confidence, ambiguous, stale, error. Different messages and cache rules per class.
  6. Use a per-channel/per-shape token budget. 192 tokens is fine for voice, but it truncates lists and fee tables in chat.

9.6 Fix operations, observability and evaluation

  1. Boot readiness report (logged and on /health): mode, deep search, revalidation, graph nodes/pages/shells/docs done/pending, chunks, embeddings, embedding provider, scheduler, last compile/refresh. Warn when NGA_ENABLED=true but the mode is not agentic, when deep search is on but the index is empty, or when a batch writer holds the serving DB.
  2. Turn trace with a reason code for every path: answered, cache_hit, deep_search, static_fallback, no_evidence, blocked, policy, error. Include retrieval scores, relevance-gate result, evidence IDs and cache key.
  3. Outcome evaluation, not component tests: a frozen conversation set with the exact failing utterances and follow-ups; expected shape (answer/clarification/refusal) + required facts + forbidden claims + citations; run against the live graph nightly; metrics for grounded-answer rate, false-refusal rate, irrelevant-evidence rate, blocked rate, cache-hit correctness, follow-up success, p95 latency; shadow mode and canary for any retrieval change.
  4. Deployment gates: a phase is “done” only when the code is wired in the live seam, the flags are on in the target environment, the store is populated, the E2E evaluation passes, and rollback is tested. Update the status vocabulary to designed / coded / wired+enabled / verified.
  5. Keep the indexer out of the serving DB or use an atomic snapshot swap/Postgres. A live answer must never wait on a batch writer.

11

Mistake ledger

Rules for the next solution, derived from this failure.

  1. Fix the contract before the machinery. If the decision “is this evidence adequate?” is wrong, a better retriever, cache or verifier downstream will not save the turn.
  2. Measure the live path, not the component. A unit test with a fake LLM and a one-page fixture is not evidence that the user’s question works.
  3. Treat irrelevant evidence as equivalent to no evidence for the purpose of exploration. The deep-search trigger must use a relevance/adequacy predicate.
  4. Never cache a non-answer as a positive answer. A refusal is a result, not a verified fact.
  5. A flag is not a capability. “Implemented” means wired, enabled, populated and verified end to end. Check effective config at boot and in CI.
  6. Do not share the serving store with a batch writer. SQLite is not a queue; a backfill must not make a chat turn wait 30 seconds.
  7. Do not derive a universal entity detector from a fee table. Programme detection (UG/PG/PhD, departments), lead capture and fee grounding are three different universes.
  8. A shell is a navigation node, not a non-existent node. Distinguish “cannot ground” from “cannot navigate.”
  9. Do not let the LLM’s refusal be the only abstention signal. Classify the answer state before generation; validate adequacy after generation; use a repair loop.
  10. Do not ship a retrieval upgrade without an E2E outcome test on the exact failing conversations and the frozen evaluation set.
  11. Do not let the static path silently answer when the agent path fails. Surface the path and reason; the static corpus is smaller and older.
  12. Do not confuse “the verifier found no false claim” with “the answer is correct.” Safety and adequacy are different axes.
  13. Do not let a status document create false confidence. Say “coded” vs “live” and link the E2E evidence.
  14. Do not fix the site’s content problem with retrieval alone. If the page is an image/JS shell, HTML chunking and embeddings cannot see it. Decide the acquisition strategy per content shape.

One-paragraph conclusion

The recent solutions did not fail because they were badly built. They failed because they were built one layer too low. The system decides, before any of them run, that a conversation move is a knowledge query, that a shell page does not exist, that any retrieved text is adequate evidence, and that a refusal with no false claim is a verified answer. Those four decisions produce the observed experience. The next solution should start by making them explicit — conversation frame, navigation answerability, evidence adequacy, and answer state/cache semantics — and only then re-enable the retrieval, chunking, embedding and deep-search machinery behind an end-to-end evaluation that uses the failing conversations as the acceptance test.
