Research result

Status updates hinge on a userId you can only get by creating one

PATCH /users/{user_id}/status needs a Salesforce Customer.Id, and the only endpoint that returns one is POST /users/lookup-or-create. There is no GET /users/{user_id} anywhere in the API.

Three things follow, and they shape the entire design:

  • The userId must be captured at conversation start and persisted. It cannot be fetched later — so a CRM identity is a per-session prerequisite, not a lookup you do when you need it.
  • There is no read-back path. To re-read a user's current CRM state you must call lookup-or-create again — a POST that can create a record if the lookup misses. Any "refresh status" feature inherits the duplicate-creation risk.
  • Only three fields are writable: sentiment, offerLetterReleased, offerLetterAccepted. Everything else is write-once at create, or not exposed. There is no generic status field.

The good news: this app already computes all three signals. No new inference work is needed — the integration is a wiring exercise.

The field you would reach for is the wrong one

Two of the three status fields are restricted picklists

Verified live against the dev org — 202 existing rows, then round-tripped by the verification script:

FieldAccepted values
Sentiment__c NURTURE · HOT · WARM · AT-RISK · DISQUALIFIED
Offer_Letter_Accepted__c UNKNOWN · ACCEPTED · NOT_ACCEPTED
Offer_Letter_Released__c boolean
Course__c free text — a value of "Verify Program" was accepted

The obvious source field for sentiment is primary_emotion from app/sentiment/scorer.py:95 — excited, interested, neutral, skeptical, frustrated, angry, confused. That set shares zero values with the picklist.

The correct source is the categorizer (app/sentiment/categorizer.py:31–35), whose five outputs map cleanly by upper-casing — and whose At-Risk already hyphenates to match. The script proved both halves: a mapped value round-trips, and a raw 'excited' is rejected.

Why this is dangerous rather than merely annoying

An out-of-vocabulary value fails as a 500, not a 400. R4 already warned that a 500 can mean "created but response failed". R16 shows the same code also means permanent validation error. The outbox has to parse detail and refuse to retry a RESTRICTED_PICKLIST failure — because retrying forever is exactly what it will do by default.

Near-miss to watch: Sentiment__c uses AT-RISK with a hyphen; the separate Lead_Category__c field uses AT RISK with a space. Any copy-paste between them fails.

Four gaps the plan must close

  • G1 — Inbound voice has no caller number. The webhooks declare no From parameter and the TwiML <Stream> carries no custom parameters. Twilio Media Streams doesn't include the caller number in its start event, so it must be captured at the webhook and threaded through via <Parameter>. This is the same defect already logged as B6 in doc/environmentsetup/OPEN_QUESTIONS.md — fixing G1 clears B6.
  • G2 — Outbound voice loses the lead at the WebSocket boundary. The lead is resolved before dialling (app/outbound/caller.py:153–161) but the handler reads only callSid/streamSid.
  • G3 — No conversation ID exists at conversation start. The UUID is minted at write time, after the call ends — app/leads/models.py:392, reached from _handle_disconnect. Since conversationId is required by the API, a stable ID must be minted at session start instead.
  • G4 — Voice has no email. A call gives a phone; email arrives later or never. Sending "" is actively dangerous — see R2.

R1 Critical Users and admissions are the same object

/users and /admissions both write the Salesforce Customer object. One person can hold two rows, and GET /admissions returns user rows too — unfiltered. A lookup can therefore hand back an admission application as if it were the user.

salesforce_user_repository.py · salesforce_admission_repository.py
R2 Critical Lookup matches on OR, with LIMIT 1 and no ordering

find_user queries WHERE Email__c = X OR Phone__c = Y LIMIT 1. Two failures compound: an empty value makes the clause Email__c = '', matching unrelated records; and when several rows match, which one comes back is undefined. Combined with G4 — voice calls have no email — a naive integration will mis-link or fabricate users.

salesforce_user_repository.py: find_user
R3 High SOQL injection through the f-string

email and phone_number are interpolated straight into the query. An apostrophe breaks it; a crafted value alters it.

salesforce_user_repository.py: find_user
R4 High Partial success returns 500

The response formatter returns fields that may be None, while the response model requires them as str. A record created without an email fails response validation — after the Salesforce row was written. The caller cannot tell "created" from "failed", so any retry duplicates it.

user_service.py: format_user_response · user_schema.py: UserResponse
R5 High Find-then-create has no lock

Two concurrent inbound calls from the same number can both miss the lookup and both create. Nothing upstream prevents it. This app must single-flight instead.

user_service.py: lookup_or_create_user
R6 High Conversation_ID__c is never updated for a returning user

It is set at create time only — the existing-user branch returns early. Every new conversation leaves the CRM pointing at the first one, which defeats the stated purpose of the integration. This cannot be fully fixed from the client.

user_service.py: lookup_or_create_user
R7 High Latency, on the call-answer path

Every repository call re-runs the OAuth token fetch. One lookup-or-create can cost three token fetches and three Salesforce round trips — while the voice turn already runs 12–35s. CRM work must stay off the critical path.

app/core/salesforce.py: get_salesforce
R8 High The API has no authentication at all

No API key, no signature check, no CORS configuration. Anyone who reaches baseUrl can read, mutate and delete the entire CRM.

main.py — no middleware, no auth dependency on any route
R9 Resolved Port collision on 8000

Closed by D2 — the API runs on 127.0.0.1:8098, clear of this repo's :8000 and enterprise-rag-core's :8010. Loopback-only, which also contains R8 for now.

Decisions

Three are settled, and one of them was the big one

D1 Answered Frozen external contract — we call it, we do not change it

Every upstream defect is therefore defended client-side, and three become permanent: R2 (never send a blank identifier — client discipline is the only control), R16 (the mapping table), and R6.

R6 cannot be solved from the client at all. The CRM will keep showing the first conversation for a repeat caller, so the authoritative linkage stays local and the CRM's conversation field is treated as stale-but-harmless. Worth telling whoever consumes the CRM: any report keyed off that field will be wrong for repeat callers.

D2 Answered http://127.0.0.1:8098, running locally

Source at D:\project\salesforce\salesforce-admission-api. No port collision, so R9 is dead. Loopback-only — which contains R8 for now, but that containment ends the moment it moves anywhere reachable, so D5 still matters.

D3 Answered offerLetterAccepted vocabulary confirmed

UNKNOWN · ACCEPTED · NOT_ACCEPTED — so the app's "rejected" maps to NOT_ACCEPTED.

D8 New Should the destructive R2/R4 probe be run?

Phase 0 deliberately skipped it. It is the only way to confirm whether a blank-identifier lookup matches an unrelated record (R2) or creates-then-500s (R4) — but if R4 fires, the record exists and this API cannot delete it, because there is no GET /users/{id} to find it with.

Recommendation: run it against a sandbox org, not the one under test. Until then R2 and R4 stay source-read rather than reproduced.

D4 Phase 3 WhatsApp session idle window

Proposed default: six hours. What makes two threads one conversation?

D5 Before prod Is a shared-secret header acceptable, or network isolation alone?

Worth stating plainly: the whole CRM is readable and deletable by anyone who reaches the port. Loopback-only is the sole control today.

D6 Phase 8 Compliance sign-off for student PII

Ties to R12 and the unanswered retention and consent questions.
